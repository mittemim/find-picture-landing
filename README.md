# Картина без происхождения

Учебный мини-сайт на Next.js: закрытая галерея принимает первичные обращения по делу о картине без происхождения. Посетитель оставляет контактное лицо, телефон для связи и ожидание по вознаграждению за наводку.

## Границы мини-проекта

Одна страница с тремя секциями:

- **«Витрина дела»** — представление картины и краткая сюжетная справка.
- **«Основания для контакта»** — пояснение, с какой наводкой можно обратиться в галерею.
- **«Первичный запрос»** — форма обращения и результат отправки.

Страница задумана как один экран на широком дисплее. На небольших экранах секции располагаются последовательно с прокруткой.

## Форма

Только три пользовательских поля:

| Поле | Назначение | Базовая проверка |
| --- | --- | --- |
| Контактное лицо | Как обращаться к посетителю | От 2 до 20 символов после удаления пробелов по краям; буквы, обычные пробелы, дефис и тире `–`/`—`; хотя бы одна буква |
| Телефон для связи | Номер для обратной связи | Ровно 11 цифр, первая — `7` или `8`; пробелы, `+` и другие символы запрещены |
| Вознаграждение за наводку | Ожидаемая сумма в рублях | Обязательное неотрицательное число, не более 7 символов; допустима точка или запятая для дробной части (входит в лимит); `0` означает без вознаграждения |

При превышении 7 символов форма предлагает обсудить вознаграждение после личного общения и передачи сведений, в зависимости от их ценности. Буквы в имени допустимы на любом языке; имя из одних пробелов и тире не принимается.

Клиентская валидация показывает ошибки рядом с полями. Во время отправки повторная отправка блокируется. После ответа посетитель видит подтверждение приёма или понятное сообщение об ошибке.

## Приём и хранение обращения

- Next.js с App Router и TypeScript.
- API-роут `POST /api/requests` принимает JSON с полями `contactPerson`, `phone`, `reward`.
- Серверная Zod-схема независимо проверяет все три поля и отклоняет неизвестные поля.
- Невалидный запрос возвращает `400` и не сохраняется. Успешное сохранение возвращает `201`. Ошибка хранения возвращает `500` без внутренних подробностей.
- Валидная запись сохраняется в локальную SQLite через параметризованный запрос. Серверный обработчик работает в Node.js runtime.
- Файл базы хранится вне публичных файлов сайта и исключается из Git вместе с сопутствующими файлами SQLite.
- В базе хранятся `id`, `contact_person`, `phone`, `reward` и `created_at`. Дата и время создаются SQLite при вставке в формате UTC ISO 8601, например `2026-10-25T09:15:30.123Z`; пользователь их не передаёт.
- SQLite доступна через встроенный модуль Node.js `node:sqlite`. Каталог и таблица создаются автоматически при первом валидном обращении. Соединение закрывается после записи.
- По умолчанию файл базы — `data/requests.sqlite` относительно корня проекта. Для другого пути задайте серверную переменную `SQLITE_PATH`. Для сохранности данных между перезапусками используйте один и тот же путь на локальном диске.

Пример тела запроса (все три входных значения — строки):

```json
{ "contactPerson": "Анна-Мария", "phone": "79991234567", "reward": "15000" }
```

При ошибках полей ответ `400` содержит `message` и `errors` с сообщениями для соответствующих полей. Повреждённый JSON также отклоняется с `400`. Данные обращения и служебные поля не возвращаются в ответах API.

## Контрольный просмотр

Node.js-скрипт `scripts/view-requests.mjs` читает сохранённые записи из SQLite и выводит только:

- контактное лицо;
- телефон для связи;
- вознаграждение за наводку.

Идентификаторы, время создания и другие служебные данные в вывод не включаются. Скрипт предназначен для локального контрольного просмотра, отдельная веб-страница со списком обращений не требуется.

Запуск из корня проекта:

```sh
npm run requests:view
```

Для вывода только JSON без заголовка npm: `npm run --silent requests:view`. Вывод содержит все обращения в порядке добавления, с тремя ключами: «Контактное лицо», «Телефон для связи», «Вознаграждение за наводку».

Скрипт открывает `data/requests.sqlite` только для чтения. Если у приложения настроен другой путь, передайте тот же `SQLITE_PATH` в окружении команды. Если базы ещё нет или обращений нет, выводится `[]`; отсутствующая база не создаётся. При ошибке чтения команда завершается с ненулевым кодом.

## Что не входит

Авторизация, личные кабинеты, админ-панель, загрузка файлов, дополнительные поля формы, поиск по обращениям, уведомления, платежи и выплата вознаграждения, проверка происхождения картины, интеграции с внешними сервисами и публичный продакшен-деплой.

## Критерии готовности

- На странице есть все три секции и форма ровно с тремя пользовательскими полями.
- Клиентская проверка не пропускает очевидно некорректные значения.
- Прямой запрос к API также проходит серверную Zod-валидацию.
- Валидное обращение сохраняется и остаётся в SQLite после перезапуска приложения.
- Невалидное обращение не создаёт запись.
- Контрольный скрипт выводит только три оговорённых поля.
- Секреты, зависимости, сборка и база с контактами не попадают в Git.

## Текущий этап

Реализованы адаптивный экран, общая Zod-схема для клиента и сервера, API `POST /api/requests`, сохранение валидных обращений с датой и временем в SQLite и скрипт контрольного просмотра. Форма блокирует повторную отправку во время запроса, показывает серверные ошибки и очищается только после подтверждённого сохранения. При ошибке значения остаются в полях.

### Локальный запуск

Требуется Node.js 24 или новее и npm (для встроенного `node:sqlite`).

```sh
npm ci
npm run dev
```

Откройте http://127.0.0.1:3000. Для проверки типов: `npm run typecheck`. Для production-сборки: `npm run build`, затем `npm start`.

`npm test` собирает приложение и проверяет схему, API, отсутствие записи при невалидных данных, серверную дату/время и сохранность SQLite после перезапуска. Прямые HTTP-запросы выполняются без браузера к отдельному процессу Next.js: лишние и отсутствующие поля отклоняются, после каждого отказа содержимое базы остаётся прежним. Отдельно проверяются состав вывода скрипта, отсутствие служебных полей и поведение при пустой/отсутствующей базе и ошибке чтения. Проверки используют временные базы и не затрагивают рабочие обращения.

Репродукции служат оформлением, не изображают разыскиваемую картину и не связаны с вымышленным делом.

Рабочие ветки именуются `feature/<краткое-описание-на-английском-через-дефисы>`, изменения предлагаются через PR в `main`.
